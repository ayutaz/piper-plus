# Zero-shot 話者再現「本人と分かる」計画 (2026-10-29)

作成日: 2026-10-29。ブランチ: `feat/zero-shot-speaker-identity`。状態: **P0 開始前 (事前登録)**。

## 1. 目的と前提

未知の話者の参照音声から合成した声が、**聞いて本人と分かる**水準になることを目的とする。
「別人には聞こえない」程度では目的を満たさない。

ユーザーが決めた前提 (2026-10-28〜29):

| 項目 | 内容 |
|---|---|
| 目標 | 「本人と分かる」 (§3 の判定規則で判定する) |
| モデルサイズ | TTS 本体は FP16 で 40MB 以内を維持する。参照音声側の encoder は現行の CAM++ と同程度 (約 4MB) 以内 |
| 速度 | CPU 推論 p50 の悪化は v10b ep79 の ONNX 比 +10% 以内 |
| 聞き手 | ユーザー 1 名 |
| データ | これまでと同じく商用利用可のデータだけを使う (非商用ライセンスのデータは使わない) |
| GPU 予算 | CloudRift と vast.ai で合計 $1000 まで。予算内で精度を上げ切る |

出発点 (調査済み、2026-10-28):

- 現行の最良は v10b ep79。参照融合計画 ([zero-shot-reference-fusion-plan-2026-10-17.md](zero-shot-reference-fusion-plan-2026-10-17.md)) の候補はすべて不合格だった。
- 学習に使っていない日本語話者で見ると、cross-utt の類似度は 0.60 前後で頭打ちになっている。つくよみ (学習外の別録音) は 0.72〜0.75 で、日本語女性の floor 0.70〜0.74 とほぼ同じ。正規化転写率は 0.2〜0.35。
- 話者情報の損失の 78% は decoder 段で起きている。recon bound は 0.714 で、decoder より手前をいくら改善しても上限は +0.04。FiLM の scale は sigmoid の上限 0.4998 に張り付いている。
- 過去の調査 ([zero-shot-v10-similarity-research.md](zero-shot-v10-similarity-research.md)) では、192 次元のベクトル 1 本で話者を伝える方式の転写率は 0.5〜0.6 が上限。実音声並みの類似度が出るのは、参照音声の系列そのものをモデルに見せる方式だけだった。
- 日本語の学習データには、moe-speech-plus の約 470 話者 (学習除外 10 話者を除く) がすでに入っている。学習していない日本語話者でも 0.60 で頭打ちのため、話者数より方式が律速とみる。

## 3. 最終判定規則 (事前登録)

最終判定は P4 のモデルに対して 1 回だけ行う。判定には**最終群**を使う。最終群は学習除外の日本語 5 話者 (11b1eb07、1cc3c6c0、23e5ef98、3d995663、46f336bf) とつくよみで、最終判定まで聴感でも数値でも使わない。つくよみは開発中にも数値評価で使ってきたため、聴感試験の最終群にだけ入れる。

判定は 2 段に分けて報告する。

- **合格**: 学習除外 5 話者とつくよみのどちらでも、L1〜L3 と N1〜N5 をすべて満たす。
- **部分合格**: 学習除外 5 話者では満たすが、つくよみで満たさない。

### 3.1 聴感 (主判定)

聞き手はユーザー 1 名。試験形式は §5 に従う。各試行では、話者 S の実録音 (参照) を聞いた後に試験音声を聞き、「同じ人か」を 4 段階で答える (確実に別人 / たぶん別人 / たぶん本人 / 確実に本人)。「たぶん本人」と「確実に本人」を「本人」と数える。

試験音声の条件:

| 記号 | 試験音声 | 意味 |
|---|---|---|
| R+ | S の別の実録音 | 聞き手にとっての上限 |
| R− | S と同性で声の近い別話者の実録音 | 聞き手が別人を本人と誤る率 |
| Z+ | S の参照から合成した音声 (参照とは別の文) | 合成が本人に聞こえるか |
| Z− | 別話者 S′ の参照から合成した音声 | 合成が「誰にでも似た声」になっていないか |

`H(x)` は条件 x で「本人」と答えた率とする。条件ごとに 48 試行 (6 声 × 8)。

| 規則 | 内容 |
|---|---|
| L1 | `H(Z+) ≥ 0.75` (48 試行中 36 以上) |
| L2 | `H(Z+) ≥ H(R+) − 0.15` |
| L3 | `H(Z−) ≤ H(R−) + 0.10` |
| L0 (試験の有効性) | 同じ試行を伏せて繰り返した組で、答えが一致した率が 0.8 以上。満たさないセッションは無効とし、日を改めてやり直す |

### 3.2 数値 (補助判定)

| 規則 | 内容 |
|---|---|
| N1 | CAM++ と ECAPA の両方で、正規化転写率が閾値 T 以上。T は P0-5 の規則で決め、P0 の完了時に確定する。確定までの仮の値は 0.6 |
| N2 | `goodhart_flag` と `above_ceiling_flag` がどちらも true でない (`--baseline-json` は v10b ep79) |
| N3 | CER の median が 0.30 以下 ([zs-eval-contract.md](../spec/zs-eval-contract.md) §7) |
| N4 | 音質の規則 (契約 §6)。P0-6 で comb 指標を差し替える場合は、新しい名前で P0 の完了時に登録し直す |
| N5 | TTS ONNX が FP16 で 40MB 以内、参照 encoder が約 4MB 以内、CPU p50 が v10b ep79 ONNX 比 +10% 以内 (同じ機械・同じ手順で測る) |

判定規則は P0 の完了コミット以後は変えない。変える必要が出た場合は、新しい規則として別名で登録し直し、古い規則での結果も併記する ([zero-shot-noise-root-cause-pqmf.md](zero-shot-noise-root-cause-pqmf.md) §4 の再発防止)。

## 4. P0: 判定基準と測定系

目的: これまでの判定は日本語 5 話者・seed 1 つで、ノイズ指標 (comb 超過) が聴感上のノイズと対応しているかも確かめていなかった。S5′ の不合格もこの comb 超過によるものだった。測り方を先に固め、改善とばらつきを区別できるようにする。

使う資源: ローカルの CPU と RTX 4070 Ti SUPER。GPU のレンタルはしない。

| 作業 | 内容 | 完了条件 |
|---|---|---|
| P0-1 評価音声の取り直し | 学習除外の 10 話者の音声を HF `ayousanz/moe-speech-plus` から取り直す (話者ごとの zip のみ)。つくよみはローカルの `datasets/tsukuyomi-raw/wavs` を使う | 開発 5 話者の参照 wav の sha256 が S4 の manifest (`/data/piper/eval-s4/set/groups/*/speaker/*.wav`) の記録と一致する。一致しない場合は差を記録し、新しいセットとして扱う |
| P0-2 評価セットの固定 | 開発群 (5 話者 + つくよみ) の参照・実発話・floor 話者・文を manifest に固定する。最終群は一覧だけ作り、音声は合成も試聴もしない | manifest と作成スクリプトをコミットする |
| P0-3 v10b の基準値 | v10b ep79 (HF `checkpoints-v10b/epoch=79-step=106880.ckpt`) を、推論 seed 3 つ × 参照 2 本で評価する | 指標ごとに平均と、seed・参照の違いによる幅を記録する |
| P0-4 聴感試験の道具と較正 | §5 の試験を作る道具と集計の道具を TDD で作る。開発群で、R+ / R− / Z+ (v10b) / Z− (v10b) の較正セッションをユーザーが行う | `H(R+)`、`H(R−)`、v10b の `H(Z+)`・`H(Z−)` と L0 を記録する |
| P0-5 数値と聴感の対応 | 較正セッションの答えと、同じ試験音声の SECS を照らし合わせる | T を次の規則で決める: 較正で「本人」と答えた Z+ 試験音声の正規化転写率の中央値と 0.6 のうち、大きい方。Z+ で「本人」が 5 件未満なら 0.6 とする |
| P0-6 comb 指標の確認 | 実録音と合成音声で comb 超過の分布を出し、推論 seed による幅を測る。S5′ の C0 ep39 と C0-self ep39 の音声を伏せて聞き比べ、ノイズの多い方を選ぶ試験を行う (20 組) | 次のどちらかを記録する: comb 指標を続けて使う (聞き比べで comb 超過の大きい方を選んだ率が 0.7 以上)、または差し替える (新指標を別名で登録する) |
| P0-7 decoder 段の診断 | v10b ep79 と S5′ の ckpt で、話者情報が decoder のどの層で失われるかを測る。層ごとの FiLM scale の張り付きも調べる | 損失の大きい層と、その量を記録する。P1 の注入先の根拠にする |
| P0-8 pt `ã` の確認 | `ã` (U+00E3) が音素 ID 表になく、学習・推論の両方で黙って落ちているかを確かめる | 落ちていれば、P4 の学習データを作る前に直す方針 (ID 追加とランタイムへの影響) を記録する |

P0 の完了条件: P0-1〜P0-8 の完了条件をすべて満たし、T と N4 の扱いを確定させた版の本書をコミットする。

## 5. 聴感試験の形式

- 試験はブラウザで開く静的な HTML とし、音声と一緒にローカルに置く。答えは JSON で保存する。
- 試行の順番は乱数で決め、条件・話者・モデル名はファイル名からも分からないようにする (ハッシュ名にする)。
- 合成音声は参照とは別の文にする。実録音も、参照とは別の発話を使う。
- 聞きやすさを揃えるため、すべての試験音声に同じ音量の正規化をかける (実録音も同じ)。数値の測定は契約 §2-5 に従い、正規化前の素の出力で行う。
- 1 セッションの 10% の試行を、伏せたまま繰り返す (L0 の確認用)。
- 1 セッションは 40 分以内とする。それより長くなる場合は日を分ける。
- 道具は判定の閾値を持たない。集計の道具が出した率を、本書の規則に照らして人が判定する。

## 6. P1 以降の概要

### P1 方式設計

- 参照音声を短い特徴の列 (数十フレーム程度) に変え、decoder がそれを cross-attention で参照する方式を主候補とする。注入先は P0-7 の結果で決める。
- 参照音声の処理は話者ごとに 1 回で済ませ、結果を使い回せる形にする。こうすると、1 発話あたりに増える計算は decoder 内の参照だけになる。
- 小さな変更の候補として、FiLM の上限を外す方式 (`--film-free-scale`) を単独で試す。v11 の中でしか試しておらず、単独の効果は確かめていないため、P2 の比較群に入れる。
- 固定 encoder の点数を学習の目標にしない ([zs-eval-contract.md](../spec/zs-eval-contract.md) §2-4)。
- ゴール: 試作 ONNX (重みはランダム) で N5 を実測する。6 ランタイムの変更範囲を見積もる。P2 の比較群・epoch 数・seed 数・合格条件を事前登録する。

### P2 小規模比較

- warm restart では判断しない (v9 の 7 介入で、warm restart では転写能力が戻らないと確定済み)。全群を from-scratch で、同じデータ・同じ epoch で学習する。
- 対照群 (現行方式) を seed 違いで 2 本以上学習し、学習のやり直しによる指標の幅を測る。G5′ で分からなかった「comb 超過の run 間のばらつき」もここで測る。
- 合格の目安 (P1 の終わりに確定する): 開発群の正規化転写率が、両方の encoder で対照の平均を学習のやり直しによる幅の 2 倍を超えて上回る。N2〜N4 で悪化しない。開発群の聴感で `H(Z+)` が上がる。

### P3 データ拡充 (条件付き)

- 行うのは、P2 で学習除外話者 (moe-speech-plus と同じ録音条件) は改善したのに、つくよみ (別の録音条件) が改善しなかった場合とする。
- 候補は商用利用可の日本語コーパスと、Common Voice ja (CC0) のような録音条件の幅が広いデータ。ライセンスは採用前に 1 件ずつ確認し、一覧に記録する。非商用ライセンス (例: Emilia) は使わない。
- ko を戻すかどうかもここで判断する。

### P4 本学習

- from-scratch で学習する。epoch 数と seed 数は P2 の結果で決める。予算内なら 2 seed を学習し、両方を報告する。
- 中間の確認点と停止条件 (R3) を学習開始前に本書へ登録する。運用は `/remote-train-ops`、評価は `/eval-zs` の手順に従う。

### P5 書き出し・ランタイム・公開

- ONNX の入力が増えるため、6 ランタイム (Python / Rust / Go / C# / WASM / C++) を対応させる。旧モデルは今まで通り動くようにする。
- ランタイム間の一致検査を CI に入れ、`/publish-model` で公開する。

## 7. 実施記録

### 7.1 P0-1 評価音声の取り直し (2026-10-29、完了)

- 開発 5 話者の zip を HF `ayousanz/moe-speech-plus` (revision `691d8a2b5c6cc9352904a0639942d3ce74c89a02`) から取得した。最終群 5 話者の音声は取得していない。
- S4 の記録 (E0 の `eval_zs_secs` report に残った sha256) にある 60 ファイル (参照・cross 用の実発話・floor) が、zip 内の原音とつくよみの wav に**すべてバイト単位で一致**した。録音は加工せずにそのまま使われていた。
- 参照の CAM++ embedding (`cpu_reference_comparison.reference_embedding`、trim なし) は VM の記録と sha256 が一致しなかった。同じ関数の 2 つの呼び方は手元で差 0.0 なので、計算の手順ではなく、OS・CPU による浮動小数点の端数の違いとみる。同等性は 7.3 の SECS の一致で確かめた。

### 7.2 P0-2 評価セットの固定 (2026-10-29、完了)

- 仕様 JSON: `scripts/evaluation/zs_identity/dev_set_s4.json` (schema `zs-eval-set-v1`、開発群 6 群、各群は参照 2 本・cross 用の実発話 8 本・floor 8 本、6 文 × 参照 2 本 = 72 clip)。
- 組み立て: `python -m piper_train.tools.build_zs_eval_set`。群ごとの評価: `python -m piper_train.tools.run_zs_eval_set` (第 2 encoder は必須)。
- floor は「他の開発話者の実発話 2 本ずつ」(つくよみは 361eb7a2・673810f3 から 4 本ずつ) で、声の近さで選んだものではない。聴感試験の R− と Z− もこの floor 話者を使う。

### 7.3 P0-3 v10b の基準値と測定のばらつき (2026-10-29、EMA 分は完了)

条件: v10b ep79 (`checkpoints-v10b/epoch=79-step=106880.ckpt`、sha256 `27a2599b…`)、torch-ema、scales [0.4, 1.0, 0.5]、ローカル RTX 4070 Ti SUPER。seed 42/43/44 の 3 回と、S4 の VM (RTX 5090) の seed 42 を並べた。

| 指標 | 日本語 5 話者の平均 (手元 s42 / s43 / s44 / VM s42) | 平均の振れ幅 | 話者 1 人の振れ幅 (最大) |
|---|---|---|---|
| CAM++ 正規化転写率 | 0.257 / 0.236 / 0.244 / 0.262 | 0.026 | 0.123 (6e22f5cd) |
| ECAPA 正規化転写率 | 0.211 / 0.241 / 0.219 / 0.216 | 0.030 | 0.077 (6b2b26d1) |
| comb 超過 (6 群平均、dB) | 2.05 / 1.92 / 2.15 / 1.97 | 0.24 | 0.67 (6e22f5cd) |

つくよみ: CAM++ 0.224 / 0.178 / 0.195 / 0.272 (振れ幅 0.094)、ECAPA 0.168 / 0.091 / 0.081 / 0.244 (振れ幅 0.162)。`goodhart_flag` と `above_ceiling_flag` は全 run で true なし。

torch-raw でも振れ幅は同じ程度だった (日本語 5 話者の平均で CAM++ 0.253 / 0.254 / 0.251 / 0.265 = 振れ幅 0.014、ECAPA 0.185 / 0.226 / 0.211 / 0.196 = 0.041、comb 2.20 / 2.07 / 2.21 / 2.08 dB = 0.14 dB)。

読み取り:

- 同じモデル・同じ参照でも、合成時の乱数 (seed と GPU の違い) だけで、日本語 5 話者の平均が約 0.03、話者 1 人では最大 0.12〜0.16 動く。
- G4 の「native ECAPA で +0.01 以上」や群間の ±0.01 の差は、この振れ幅の中にある。参照融合計画の判定のうち、この大きさの差に頼った部分は、測定のばらつきと区別できていなかった。
- G5′ を不合格にした comb 超過の差 (C0 2.74 dB 対 C0-self 1.68 dB) は、合成時の振れ幅 (0.24 dB) の 4 倍以上ある。合成の乱数では説明できない。学習のやり直しによる幅は P2 で測る。
- つくよみ 1 声だけの値は 0.09〜0.16 動く。これまでの「つくよみで +0.03」のような結論は、振れ幅の中にある。
- P2 以降の比較では、seed 3 つ以上の合成をまとめて評価する。差の判定には、この節の振れ幅と、P2 で測る学習のやり直しによる幅を使う。

### 7.4 P0-4 聴感試験 (2026-10-29、道具は完了、較正セッションは未実施)

- 道具: `python -m piper_train.tools.listening_identity build / score`。
- 較正セットは、開発群 6 声 × 4 条件 × 8 試行 = 192 試行に、繰り返し 10% を足したもの。3 セッション (各 70 試行) に分けた。Z+ と Z− の合成音声は v10b ep79 torch-ema の seed 42/43/44 から選んだ。答え合わせの対応表は、ページとは別の directory に置いた。
- 試聴用の音声は 22.05kHz に揃えて RMS を -23 dBFS にし、16bit で書いた。実録音 (48kHz など) と合成の帯域差で、合成だと分かってしまうのを防ぐため。

### 7.6 P0-7 decoder 段の再構成 (2026-10-29、v10b EMA で完了)

方法 (`python -m piper_train.tools.measure_recon_bound`): 各群の実発話 10 本を、評価セットの cross 用とは別に選んだ (moe-speech-plus は 3〜10 秒を path 順に、評価セットとの sha256 重複なし。つくよみは VOICEACTRESS100_011〜020)。学習と同じ前処理 (`cache_norm_audio_fast`) で spec にし、`enc_q` → decoder に直接通した (prior・flow・duration は通らない)。

- own: `enc_q` も decoder も、その群の参照 (ref0) の g。
- swap: `enc_q` はその群の g、decoder だけ別の群の g (開発話者を順に入れ替え、つくよみには 361eb7a2)。

正規化転写率 (`eval_zs_secs`、TTS は seed 3 つの平均):

| 群 | CAM++ TTS | CAM++ own | CAM++ swap→元話者 | ECAPA TTS | ECAPA own | ECAPA swap→元話者 |
|---|---|---|---|---|---|---|
| 日本語 5 話者の平均 | 0.245 | 0.297 | 0.115 | 0.224 | 0.061 | −0.023 |
| つくよみ | 0.199 | 0.260 | 0.273 | 0.113 | 0.380 | 0.377 |

再構成が元の発話をどれだけ保つか (CAM++ cosine の平均):

| 群 | 再構成 ↔ 元の発話 | 元の発話 ↔ 同じ話者の別の発話 (cross) | 再構成 ↔ cross |
|---|---|---|---|
| 361eb7a2 | 0.681 | 0.753 | 0.657 |
| 673810f3 | 0.621 | 0.700 | 0.621 |
| 6b2b26d1 | 0.654 | 0.747 | 0.594 |
| 6e22f5cd | 0.627 | 0.696 | 0.542 |
| 75e27ad3 | 0.734 | 0.770 | 0.661 |
| つくよみ | 0.744 | 0.866 | 0.714 |

読み取り:

- つくよみの own の cross-utt SECS は 0.714 で、v11 設計 §10.1 の recon bound (0.714) と一致した。
- **実音声を事後エンコーダー → decoder に通して戻すだけで、元の発話との類似度は 0.62〜0.74 まで落ちる。** これは「同じ人の別の発話」との類似度 (0.70〜0.87) より低い。decoder は、正しい潜在表現を受け取っても入力の声を描き直せていない。話し方のずれでは説明できない。
- 上流 (prior・flow・参照の条件付け) をどれだけ改善しても、正規化転写率は own の水準 (CAM++ で約 0.3) を大きくは超えない。§3 の目標 (仮の T = 0.6) には、**decoder の描き直しの忠実さを上げることが必須**。P1 の主な対象は decoder とする。
- swap では、decoder の g を替えると元の話者から離れる (日本語 CAM++ 0.297 → 0.115) が、decoder 側の話者には近づかない (CAM++ 0.136、ECAPA −0.185)。つくよみでは decoder の g を替えてもほぼ変わらない。decoder の条件付けは声の主を「描き分ける」働きをしていない。
- comb 超過は own では日本語 0.69 dB、つくよみ 0.82 dB (実録音 0.81 dB) で、実録音並み。TTS の約 2.0 dB は、decoder 単体ではなく、prior から作った潜在表現を decoder に入れたときに出る。
- 制約: 日本語の ECAPA own が TTS より低い群がある (361eb7a2 −0.29 など)。CAM++ と ECAPA で向きが違うため、ECAPA 単独の own の値は判断に使わない。torch-raw では未測定。

### 7.5 P0-8 pt `ã` と記号の欠落 (2026-10-29、確認済み)

学習データを作る経路 (`prepare_multilingual_dataset._phonemize_single`) と、現在の ID 表 (`get_phoneme_id_map("ja-en-zh-es-fr-pt")`、185 記号) で確かめた。

- pt の `ã` (U+00E3) は ID 表になく、黙って落ちている (例: `mão` → `m u`)。ほかの鼻母音 `ẽ ĩ õ ũ` と、`ã` の IPA `ɐ̃` (PUA U+E064) は表にある。
- **ja 以外の 5 言語 (en / zh / es / fr / pt) で、空白・`,`・`.` も落ちている** (es の `¿` も同様)。表にある記号は `?` だけ。モデルは単語の区切りも、読点・句点の位置も見ずに学習している。
- 影響は間の取り方や自然さで、話者の似方 (本計画の主目的) とは別の問題。ただし、直すには ID 表への追加が必要で、既存モデルとの互換が崩れる。P4 は from-scratch で学習し直すため、P4 の学習データを作る前にまとめて直す。直し方 (G2P 側で `ã` を `ɐ̃` にするか ID を足すか、記号の ID の追加、各ランタイムの G2P と ID 表の扱い) は P1 で決める。
