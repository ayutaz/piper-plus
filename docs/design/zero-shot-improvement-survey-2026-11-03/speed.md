## 0. 結論 (先に要点)

1. **今の CPU 推論の設定で、すぐに取れる速度はほとんど残っていません。**
   - FP16 と FP32 の推論速度は同じでした [実測]。ORT はモデルを読み込むときに FP16 の重みを FP32 に戻すため、計算はもともと FP32 です。
   - スレッド 4 は今回の PC でも最適付近でした。スピン待ちを切る設定、非正規化数を 0 に丸める設定は、どちらも測定の揺れの範囲で差が出ませんでした [実測]。
2. **INT8 量子化は、そのままでは使えません。**
   - 動的量子化 (ORT の `quantize_dynamic`) は **約 10 倍遅く**なりました [実測]。
   - 静的量子化 (QDQ) をモデル全体にかけると −22% 速くなりました。ただし、デコーダーを量子化すると 4 kHz 以上の帯域のエネルギーが **+7.4 dB** 増えました。これは新しいノイズが乗ったということです [実測]。
   - 量子化して質を保てる見込みがあるのは flow だけです。flow だけの静的 INT8 は −8〜13% 速くなりました [実測]。音の質は、正式な評価をまだしていません。
3. **速くするための一番大きな手は、モデル側の flow を小さくすることです。**
   - flow は 1 スレッドの測定で推論時間の約 29% を占め、パラメータ数でもモデルの半分 (1,008 万) です [実測]。
   - P1 設計の測定では、flow を 4 段から 2 段にすると −18.1%、幅を 192 から 128 にすると −16.9%、両方で −28.1% でした [過去実測]。
   - 音の質を保てるかは、まだ一度も学習して確かめていません。今の zs-v1 を先生役にした蒸留で質を取り戻す案が、筋が良いと考えます。
4. **ブラウザ (WASM) はマルチスレッドが使われていない可能性が高いです。**
   - ネイティブの測定では、1 スレッドから 4 スレッドにすると約 2 倍速くなりました [実測]。
   - onnxruntime-web は「crossOriginIsolated」の状態でないとスレッドを使えません。デモのページはこの状態になっていないと推測しています。
   - この修正は WASM だけで済み、音の質への影響はありません。
5. **学習の速度で最初に試す価値があるのは、パディング長をそろえる案です。**
   - 中身は「バッチのパディング長を決まった刻みに切り上げてから、cuDNN のカーネル探索を有効に戻す」です。
   - 上限の目安は、PR #815 の測定にある固定長と可変長の差 (0.50 と 0.61 s/step、約 −18%) です [過去実測からの推測]。
   - 「長さのバケット分け」とは別物です。バケット分けは学習データの組み方を変え、+34% 遅くなって不採用になっています。こちらはデータの組み方を変えず、パディングを足すだけです。
   - VITS の学習で重いデコーダーと識別器は、もともと 8192 サンプルの固定長の切り出しで動いています。そのため、フレーム総数でバッチを組む方式 (動的バッチ) から得られる利得は小さいと考えます [推測]。

## 1. 今回の測定 (このPC、CPU)

環境は次のとおりです。
- AMD Ryzen 9 5900X (12 コア 24 スレッド)、Windows 11、onnxruntime 1.30.0 (Python)、CPUExecutionProvider。
- 入力は `verification.json` にある日本語の文「こんにちは。今日は良い天気ですね。」の音素 ID を使いました。この ID 列を 1 回 (74 ID、1.51 秒) または 3 回つなげて (218 ID、4.06 秒) 入力しました。
- 結果を比べやすくするため、`scales=[0, 1, 0]` で乱数を止めています。
- 数値は 30〜40 回の中央値 (p50) です。同じ設定を繰り返しても ±5〜10% 揺れました (PC 上で他の作業も動いていたため)。

### 1.1 FP16 と FP32

| モデル | スレッド | 218 ID の p50 | 読み込み時間 |
|---|---|---|---|
| base.onnx (FP16 保存) | 4 | 113.6 / 114.2 / 111.9 ms (3 回) | 3.2〜3.4 s |
| FP32 で書き出し直したもの | 4 | 114.8 / 109.7 ms | 2.3 s |
| base.cpu.opt.onnx (キャッシュ、最適化なしで読み込み) | 4 | 132.2 ms (他の作業と重なった回) | 2.7〜3.2 s |
| base.onnx | 1 / 2 / 6 / 8 / 12 | 230 / 148 / 109 / 131 / 122 ms | — |

- 元の FP16 グラフには Cast が 513 個ありました。ORT が最適化した後のグラフ (`base.cpu.opt.onnx`) では Cast が 13 個に減り、重みはすべて FP32 になっていました (ファイルの大きさも 40.8 MB → 80 MB) [実測]。つまり CPU での計算は最初から FP32 です。
- **FP16 の利点は、ダウンロードの大きさが半分になることだけです。** 代わりに、初回の読み込みが約 1 秒遅くなります。この遅れは `.opt.onnx` のキャッシュがほぼ打ち消しています。
- 過去の P1 文書の測定でも、ピークメモリ 195 MiB のうちモデルの分 145 MiB は「セッション作成時の重みの展開」でした。メモリの面でも FP16 と FP32 の差はありません。
- ORT 側の説明と一致します。
  - ORT のメンテナーは、CPU 実行プロバイダーには FP16 の演算がなく、Cast が入るので FP16 の方が遅くなることもある、と書いています ([onnxruntime#14827](https://github.com/microsoft/onnxruntime/issues/14827), 2023-02 のコメント)。
  - ORT の公式文書にも同じ説明があります ([Float16 and mixed precision](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html))。
  - sherpa-onnx の測定 (MacBook、1 スレッド) では、piper libritts_r-medium の RTF が FP32 0.114、FP16 0.123、INT8 0.320 でした ([k2-fsa/sherpa-onnx#2460](https://github.com/k2-fsa/sherpa-onnx/pull/2460), 2025-08-07) [外部]。
- スレッドは 4〜6 が最速で、8 を超えると遅くなりました。契約 (`docs/spec/ort-session-contract.toml` の `max_intra_threads = 4`) は妥当です。

### 1.2 どこに時間がかかっているか (ORT のプロファイル、キャッシュ済みモデル、1 スレッド)

| 部分 | 74 ID | 218 ID | パラメータ数 |
|---|---|---|---|
| flow (事前分布の変換) | 28.8% | 28.8% | 1,025 万 (WN 部分 1,008 万 + 0.17 万) |
| テキストエンコーダー enc_p | 23.6% | 24.6% | 642 万 |
| デコーダー全体 (resblock / 拡大 / iSTFT / PQMF など) | 約 30% | 約 34% | 211 万 |
| 継続長予測 dp (確率的、内部に flow 4 段) | 12.7% | 7.7% | 75 万 |

- 演算の種類別では、Conv が約 56〜59%、ConvTranspose が約 10〜12% でした。
- iSTFT (ConvTranspose 1 個) は 1.3〜1.5%、PQMF は 1〜2% です。どちらも軽く、ここを工夫しても得るものはありません。
- デコーダーはすでに小さくなっています (MB-iSTFT、211 万パラメータ)。重さの中心は flow とテキストエンコーダーにあります。
- 4 スレッドでプロファイルを取ると、dp とエンコーダーの細かい演算の起動の手間が目立ちました (dp のノード呼び出しは 1 回あたり約 2,300)。プロファイル自体が細かい演算を重く見せるので、比率は目安として扱ってください。

### 1.3 INT8 量子化 (今回初めて試しました。過去に例はありません)

FP32 のモデルを `quantize_dynamic` と `quantize_static` (QDQ、重み int8 をチャネル別、活性 uint8、日本語/英語 × 3 つの長さで校正) で変換しました。

| 版 | 4 スレッド p50 (218 ID) | 1 スレッド p50 | 質のチェック (FP32 との比較) |
|---|---|---|---|
| FP32 | 110〜115 ms | 222〜237 ms | 基準 |
| 動的 INT8 (Conv も含む = ConvInteger) | **1,574 ms (約 10 倍遅い)** | 3,634 ms | — |
| 動的 INT8 (MatMul のみ) | 117 ms | 219 ms | **継続長の合計が −2.9% ずれた** (話す速さが変わる) |
| 静的 QDQ、全体 | **88〜90 ms (−22%)** | 148 ms | 高域 (>4 kHz) のエネルギー **+6.9 dB** |
| 静的 QDQ、デコーダーのみ | 128 ms (誤差の範囲〜やや速い) | — | 高域 **+7.4 dB** (ノイズが乗る) |
| 静的 QDQ、flow のみ | **99〜107 ms (−8〜13%)** | 173〜206 ms | 高域 −0.9 dB。継続長の合計の差は +0.06% |

補足:
- FP16 版の FP32 版との差は、SNR 39.6 dB、高域の差 −0.01 dB で、実質同じ音でした。
- 量子化した版は、継続長がわずかに変わって長さが合わないため、波形の SNR は出せませんでした。高域のエネルギー差は、発話全体を合計した値で比べています。
- 動的量子化が遅いのは、Conv が ConvInteger に置き換わるためです。ORT の文書も「CNN には静的量子化を勧める」と書いています ([ORT quantization](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html))。sherpa-onnx の piper INT8 が 2.8 倍遅いのも同じ理由と見られます [外部]。
- デコーダーの INT8 は、このプロジェクトが長く追ってきた「がびがび」系の高域ノイズを、そのまま戻すことになります。**使うべきではありません。**
- flow だけの INT8 は候補として残ります。ただし、正式な評価がまだです (`/eval-zs`、帯域スペクトル、`measure_comb_hnr`、試聴)。

### 1.4 その他の設定 [実測]

- `session.intra_op.allow_spinning=0`: 4 スレッドで 104.5 / 101.8 ms。基準 111.9 / 109.0 ms に対して −4〜7% に見えますが、揺れの範囲です。
- `session.set_denormal_as_zero=1`: 104.9 / 112.5 ms で、差はありませんでした。
- 文の長さと時間の関係 (4 スレッド): 74 ID で 52 ms、218 ID で 113 ms でした。固定でかかる部分が約 20 ms あり、残りは長さにほぼ比例します。最初の音が出るまでの時間は、ほぼ「最初の文の長さ」で決まります。

### 2.1 CPU 推論

- **デコーダー**
  - #268 / PR #320 (2026-05): HiFi-GAN を MB-iSTFT に置き換えました。デコーダー単体で 168.2 → 76.2 ms (2.21 倍) です。**採用。**

- **WaveNeXt デコーダー** (tag `archive/feat/wavenext-decoder-ablation`、2026-07-14): MB-iSTFT より 24〜39% 遅く、**不採用。**
  - Vocos 系の「フレーム単位で iSTFT の係数を出す」作りは、この形ですでに負けています。
- **P1 の候補別コスト** (`docs/design/zero-shot-decoder-p1-design-2026-10-29.md` §7、道具は `piper_train.tools.measure_variant_cost`、7d97a18f)

  - デコーダー幅 384: +31%。512: +67%。n_fft 64: +18.1%。D5 (全帯域 iSTFT、幅 256): −12.6%。
  - 選んだのは K1 = D0 で、**flow は 4 段のまま**です。flow を縮める組 (Cf) は一度も学習していないため、**質のコストは不明**です。
  - P2-f (2026-11-02): K1 は v10b の 1.025 倍、C は 1.016 倍。
- **upsample の置き換え** (`--upsample-mode resize`、9b0b3106、2026-08-18): 目的は音の質 (くし形のひずみ 8.37 → 2.08 dB) でした。速さはデコーダー単体で +10.2% です。
- **v10b S-2 の F0 励振**: デコーダーが +4〜13% 遅くなりました。
- **測られずに閉じたもの**
  - VITS2 の決定的な継続長予測への切り替え (PR #240): 質の理由で close。速さは見込み +10〜20% のままです。
  - `quality=tiny` (PR #333): 測定なしで stale close。
  - iSTFTNet2-MB / FLY-TTS の骨組み (PR #567): forward が未実装のまま stale close (2026-09-21)。
- **蒸留と枝刈り**: 一度も試していません。
- **ORT セッション設定**
  - 統一した設定: #233 / #250 (C++ の ENABLE_ALL)、#315 (スレッド数 = min(コア数/2, 4))、#317 (`dynamic_block_base=4`)、#318 (warmup と `.opt.onnx` キャッシュ)。
  - これらの効果の数値は見込みで、実機で測った結果の欄は空のままです。
  - スレッドの伸び方 (PR #386、Apple M、100 音素): 1 → 120 ms、4 → 50 ms (最速)、8 → 74 ms。今回の Ryzen の結果と同じ傾向です。
- **INT8**: **一度も試していません** (今回が初めて)。
  - 調査文書 `docs/research/improvement-survey-2026-07-14-five-axes.md` §7.4 に「x86 VNNI 向けの静的 INT8」「WASM だけ q8」の案があります。

  - 同じ調査文書 §7.1 が最優先として挙げていた A/B です。今回、差がないことを確認しました。
- **ストリーミング**
  - 全ランタイムが文単位で区切って順に返します。
  - 文の途中で区切って復号するランタイムはありません。
  - 学習側にだけ古い分割版があります (`src/python/piper_train/export_onnx_streaming.py` / `infer_onnx_streaming.py`、45 フレームずつ、前後 10 フレームの余白)。
  - 調査文書 §7.5 は、文の途中で区切る案を「区切り目にひずみが出る」として退けています。

- **WASM**
  - onnxruntime-web 1.30.0 を使っています。
  - WebGPU (PR #246) は、入力が int64 のため常に WASM に戻り、TTS では実質使われていません。

- **その他**

### 2.2 GPU 学習 (主な出典: `docs/design/zero-shot-v8-dataset-scaling-plan.md` §3)

- **全体**: 14.0 → 10.74 s/step (−23%、A100、batch 64) でした。
  - 効いたのは、pin_memory が無効になっていた不具合の修正、`prefetch_factor=4`、SDPA の優先順位、KL の修正です。
  - それぞれの寄与は個別に測っていません。
- **不採用 (測定済み)**
  - 長さのバケット分け: +24% / **+34%** (5.15 → 6.90 s/step)。
    - 改良版の Fix B (a5fa6f2b) は実装しましたが、測り直していません。
  - `torch.compile`: torch 2.11 と triton でクラッシュ。
  - `--precomputed-mel`: +6.5%。学習は GPU で詰まっているためです。
  - DDP の `static_graph=True`: G と D を交互に学習するため 2 回目の反復でエラー (2abe21aa)。
  - 勾配の bf16 圧縮と P2P: 効果なし。NVLink のない 4 GPU では DDP が 1 GPU より遅い (11.1 対 5.5 s/step)。
- **本当の詰まり**: `PIPER_PLUS_FORCE_CPU_ORT=1` で CAM++ が CPU で動いていたことでした (14 → 7.14 s/step)。現在は GPU で動いています。
- **Super-MAS** (PR #582): アライメント計算は 9.4 倍速くなりましたが、ステップ全体の 0.42% しかないため、全体では約 0.37% です。
  - その後、環境によっては無言で壊れた結果を返し、80 epoch を失う事故がありました。現在は実行時に検証しています。
- **cuDNN の探索を止める** (`--no-cudnn-benchmark`、ab598a8b / PR #815、2026-10-20、RTX 5090、batch 24)
  - 可変長: 1.81 → 0.61 s/step。**固定長では 0.50。**
  - 同じ PR でホスト同期を 603 → 46 回/バッチに減らし、0.540 → 0.502 s/step でした。
- **識別器のコスト**
  - 帯域分割 MRD: 1 epoch が 69 → 77 分 (L40S)。
  - WavLM 識別器を 2 ステップごと + 切り出し 16384 (v8.1): 1 ステップ約 3.4 秒で、v8 の約 2 倍。
- **採用したが単独では測っていないもの**: TF32、fused AdamW (#218 から)、MPD の `--channels-last`、`empty_cache` の削除、`.npy` キャッシュ。
- **一度も試していないもの**: フレーム総数による動的バッチ、FlashAttention、CUDA graphs、FP8。
  - テキストエンコーダーの SDPA 化 (T3 `--attn-drop-rel-v`) は合成データで +7% 遅くなりました。

## 3. 候補の一覧 (見込める利得と手間の比で並べています)

各候補について、内容、出典、どこをどう変えるか、利得とその根拠、質のリスク、各ランタイムへの影響、手間、過去に試したかを書いています。

### 【CPU 推論】

#### C1. ブラウザ (WASM) のマルチスレッドを有効にする
- **内容**: onnxruntime-web は、ページが crossOriginIsolated (COOP/COEP ヘッダーが付いた状態) のときだけ複数スレッドを使います。既定は「コア数の半分と 4 の小さい方」です ([ORT Web env flags](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html))。
  - GitHub Pages はヘッダーを設定できません。代わりに service worker でヘッダーを付ける [coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker) (MIT) が使えます。初回だけページが読み込み直されます。
- **変更点**: `src/wasm/openjtalk-web` のデモ/配布ページで COI を有効にします。`ort.env.wasm.numThreads` は 0 (自動) のまま、または明示します。
  - npm 利用者向けには `docs/guides/integration/wasm-bundler-guide.md` に設定例を足します。
  - スレッドを使えないときは、自動で 1 スレッドに戻ります。
- **利得**: ネイティブでは 1 → 4 スレッドで 230 → 113〜133 ms (約 1.8〜2 倍) [実測]。WASM での伸び方はまだ測っていません [推測: 1.5 倍前後]。
- **質のリスク**: ありません (計算は同じ)。
- **ランタイムへの影響**: WASM のみ。Python / Rust / C# / Go / C++ には関係ありません。
- **手間**: 小。
- **過去**: 設定していません。COOP/COEP は文書で説明しているだけです。

#### C2. 最初の音を早く出す: 最初の文だけ読点で短く切る
- **内容**: 最初の音が出るまでの時間は、ほぼ最初の文の長さで決まります (固定 ~20 ms + 長さに比例 [実測])。最初の文が長いときだけ、読点などで前半を切り出し、先に合成します。
- **変更点**: 各ランタイムの文分割 (`docs/spec/text-splitter-contract.toml`、Python `text_splitter.py`、Rust `streaming.rs` など) に「最初の区切りを短くする」オプションを足します。既定は off です。
- **利得**: 最初の文が 218 ID の場合、前半 74 ID で切れば、最初の音が出るまでが約 113 → 52 ms [実測の値から推測]。全体の時間は変わりません。
- **質のリスク**: 区切り目で抑揚と間が変わります (文の頭の韻律が独立してしまう)。試聴での確認が必要です。
- **ランタイムへの影響**: 6 ランタイムすべてで分割規則と fixture を同期する必要があります (contract の更新)。
- **手間**: 中 (仕様 + 6 実装 + fixture)。
- **過去**: 調査文書 §7.5 に候補として載っていますが、未実装です。

#### C3. 文の途中でデコーダーだけを区切って順に出す (余白を受容野以上にする)
- **内容**: エンコーダー、dp、flow は文全体を一度に計算し、潜在 z を区切ってデコーダーに順に通します。
  - zs-v1 のデコーダーには時間方向の平均などがなく (ReduceMean 0 個 [実測])、畳み込みだけでできています。そのため、区切りの前後の余白を「デコーダーが参照する範囲」以上にすれば、出力は区切らない場合と同じになります。
  - その範囲を設定値 (conv_pre k7、拡大 ×4 ×2、ResBlock2 の k7・膨張 (3,12) など) から計算すると、**片側約 20 フレーム** (約 0.23 秒) です [計算による推測]。
  - **古い分割版の余白 10 フレームはこれより短いので、区切り目のひずみはそのせいである可能性が高いです** [推測]。
- **変更点**: ONNX をエンコーダー側とデコーダー側の 2 つに分けて書き出します (`export_onnx_streaming.py` の考え方)。余白は 20〜24 フレームにします。
- **利得**: 長い文で、最初の音が「デコーダーの分 (約 30〜35%)」だけ早くなります。例: 4 秒の文で 113 → 約 80 ms [推測]。全体の時間はやや増えます (余白の分)。
  - 参考: 区切りながら合成する学習法の例として [Incremental FastPitch, arXiv:2401.01755](https://arxiv.org/abs/2401.01755) (2024-01) があります。
- **質のリスク**: 余白が十分なら理論上はひずみが出ません。浮動小数の誤差だけです。区切らない版との波形一致で確かめられます。
- **ランタイムへの影響**: 大。ONNX の入出力の契約が「1 モデル」から「2 モデル」に変わるため、6 ランタイムすべての読み込みとストリーミング処理を変える必要があります。
- **手間**: 大。利得は C2 と同程度なので、**優先度は低い**です。

#### C4. flow だけの静的 INT8 (QDQ) を別の配布物として出す
- **内容と出典**: 今回の測定 (1.3 節) と、ORT の量子化文書の「CNN は静的量子化」。
- **変更点**: `qstatic.py` 相当の手順を `export_onnx.py` の後処理 (例: `--quantize-flow`) にします。校正データは複数言語・複数話者にし、FP32 で書き出したモデルを入力にします。
- **利得**: −8〜13% (4 スレッド)、1 スレッドで −10〜25% [実測、揺れ大]。ファイルも小さくなります。
- **質のリスク**: 中。
  - flow は潜在変数を逆向きに変換する部分で、誤差がデコーダーに伝わります。
  - 今回は高域のエネルギー差 −0.9 dB でしたが、話者類似度 (cross-utt SECS)、CER、帯域、試聴は未評価です。
  - デコーダーの量子化は **禁止** (+7.4 dB のノイズ)。
- **ランタイムへの影響**: 全ランタイムが ORT の CPU 実行を使い、QDQ はその標準の演算です。ファイルを差し替えるだけで動く見込みです [推測、各ランタイムの ORT 版で要確認]。WASM の CPU 実行も同じ実装です。
  - 配布カタログ、モデル名の解決、`.opt.onnx` キャッシュ名は、別のファイルとして扱う必要があります。
- **手間**: 実験は小。配布まで含めると中。
- **過去**: INT8 は未経験です。

#### C5. 何もしない方が良いもの (測定で否定されたもの)
- FP16 → FP32 への切り替え: 速さは同じ。ダウンロードが 2 倍になるだけです。
- 動的 INT8: 10 倍遅くなります。
- デコーダーの INT8: ノイズが乗ります。
- スピン待ちを切る設定、非正規化数を 0 に丸める設定、スレッド数の変更: 揺れの範囲で差がありません。
- iSTFT / PQMF の実装の工夫: 合わせて 3% 未満です。
- ARM NEON の後処理: 過去に 0.5% 未満で不採用。
- WebGPU: 入力が int64 なので使えません。入力の型を変えると I/O 契約が壊れるため不可です。

### 【モデル側】(学習が必要。I/O 契約は変わらないため、ランタイムの変更は不要)

#### M1. flow を小さくし、今のモデルを先生役にして蒸留する
- **内容**: flow は時間の約 29%、パラメータの約半分を占めます [実測]。段数か幅を減らします。
  - 質を取り戻すため、zs-v1 (または v10b) を先生役にし、同じ入力で先生の flow 出力に生徒の flow を合わせる損失を足して学習します。これはモジュール単位の蒸留です。
  - 出典: [Nix-TTS, arXiv:2203.15643](https://arxiv.org/abs/2203.15643) (2022、VITS をモジュール単位で蒸留)。[sanoTTS, arXiv:2608.21378](https://arxiv.org/abs/2608.21378) (2026-07、Piper/VITS を先生役にした蒸留。145 万パラメータの版は SCOREQ 4.13 / UTMOS 4.10。最小の 57 万の版は 2.54 / 2.80 まで落ちる。容量の主な制約はデコーダーという分析)。
  - 注意: 「段の間で重みを共有する」方式 ([PortaSpeech, arXiv:2109.15166](https://arxiv.org/abs/2109.15166)、[FLY-TTS, arXiv:2407.00753](https://arxiv.org/abs/2407.00753)) は、パラメータ数は減らしますが**計算量は減りません**。FLY-TTS の 8.8 倍 (RTF 0.0139 対 VITS 0.1221、i9) は、主に ConvNeXt + iSTFT のデコーダーによるものです。piper-plus はデコーダーをすでに軽くしているので、この倍率は期待できません。
- **変更点**: `vits/models.py` の flow (`ResidualCouplingBlock`) の段数と幅の設定 + 蒸留の損失 (`vits/lightning.py`)。
- **利得**: −17〜28% [過去実測、P1 の `measure_variant_cost`]。
- **質のリスク**: 中〜大。未検証です。zero-shot の話者類似度は flow に依存している可能性があります。
- **ランタイムへの影響**: なし。ONNX の入出力が同じなので、ファイルを差し替えるだけで済みます。
- **手間**: 大 (学習)。ただし蒸留なら、ゼロから学習するより短く済む見込みです [推測]。
- **過去**: P1 でコストだけ測り、学習していません。

#### M2. テキストエンコーダーを浅くする (6 層 → 4 層など)
- **内容**: エンコーダーは時間の約 24% を占めます。層を減らします。蒸留は M1 と同じ要領です。
- **利得**: 層に比例するなら 2 層減らして約 −8% [推測]。
- **質のリスク**: 中 (発音、韻律)。
- **ランタイムへの影響**: なし。
- **手間**: 大。
- **過去**: 未実施です。

#### M3. 継続長予測を決定的なものにする
- **内容**: 確率的な dp は細かい演算が多く (1 回の推論で約 2,300 回の演算呼び出し)、時間の 8〜13% を占めます。
- **利得**: 最大 −8〜13% [実測した比率から推測]。
- **質のリスク**: 大 (抑揚の単調さ)。**過去に PR #240 が質の理由で close されています。**再提案はしません。

#### M4. デコーダーをさらに削る
- **内容**: デコーダーはすでに 211 万パラメータで、残りは約 30〜35% です。
  - 「並列の resblock を 3 本 → 2 本」などは −10% 前後の見込みです [推測]。ただし、このプロジェクトの課題 (高域ノイズ、A3) に直接響きます。
  - [Wavehax, arXiv:2411.06807](https://arxiv.org/abs/2411.06807) (2024-11、HiFi-GAN V1 の 5% 未満の計算量) や [Vocos, arXiv:2306.00814](https://arxiv.org/abs/2306.00814) 系は、WaveNeXt での失敗 (24〜39% 遅い) を考えると、速さ目的では見込みが薄いです。
- **優先度**: 低。

### 【GPU 学習】

#### T1. パディング長を決まった刻みに切り上げ、cuDNN のカーネル探索を有効に戻す
- **内容**: 可変長のままでは、毎バッチ cuDNN の探索が走って遅いため、今は `--no-cudnn-benchmark` を使っています。
  - collate でパディング長を、たとえば spec は 32〜64 フレーム、音素は 16〜32 の倍数に切り上げます。これで形の種類が数十に減り、探索結果を使い回せます。
  - バッチの組み方 (話者・言語のサンプリング) は変えません。この点がバケット分け (+34% で不採用) と違います。
- **変更点**: `vits/dataset.py` の collate (`max_spec_length` などを切り上げ)、新しいフラグ (例: `--pad-multiple`)、`__main__.py` の `configure_cudnn_benchmark`。
- **利得**: PR #815 の固定長 0.50 と可変長 0.61 s/step の差から、上限は約 −18% [過去実測からの推測]。パディングで無駄になる計算 (数 %) を差し引く必要があります。
- **質のリスク**: 低。ただし条件があります。マスクを使わずに時間方向の平均や最大を取る処理がどこかにあると、結果が変わります。導入前に、同じバッチで「切り上げあり・なし」の損失が一致することをテストで確かめる必要があります。
- **ランタイムへの影響**: なし (学習のみ)。
- **手間**: 小〜中。
- **過去**: 近い試みとして、バケット分け (不採用) と Fix B (未測定) があります。この「切り上げのみ」は未実施です。

#### T2. 識別器の重さを測ったうえで、WavLM 識別器の頻度を下げる
- **内容**: v8.1 の測定では、WavLM 識別器 (2 ステップごと、切り出し 16384) で 1 ステップが約 2 倍になりました。`--wavlm-every-n-steps 4` などで減らせます。
  - 出典: WavLM 識別器そのものは [StyleTTS 2, arXiv:2306.07691](https://arxiv.org/abs/2306.07691) が使い始めたものです。
- **利得**: 構成によっては −20〜40% [過去実測からの推測]。
- **質のリスク**: 中 (知覚品質への寄与が減る)。
- **ランタイムへの影響**: なし。
- **手間**: 小 (フラグは既存)。
- **過去**: フラグはあります。頻度と質の関係は測っていません。

#### T3. 固定長の部分 (デコーダーの切り出し + 識別器) だけを CUDA graph にする、またはコンパイルする
- **内容**: VITS の学習では、デコーダーと識別器は 8192 サンプルの固定長の切り出しで動きます (`segment_size 8192` [設定で確認])。バッチの大きさも固定なら形が変わりません。
  - PyTorch の CUDA graph は「形が変わらないこと」「CPU との同期がないこと」が条件です。条件を満たさない網には、一部だけを graph にする `torch.cuda.make_graphed_callables` が勧められています ([PyTorch CUDA semantics](https://docs.pytorch.org/docs/2.15/notes/cuda.html))。
  - 全体の `torch.compile` はクラッシュしましたが、識別器だけを `dynamic=False` でコンパイルすると避けられる可能性があります [推測]。
- **利得**: 不明。GPU への命令発行の手間が減ります。PR #815 で同期を減らしたときは −7% でした [過去実測]。
- **質のリスク**: 低 (同じ計算)。ただし weight_norm / spectral_norm のフック、G と D を交互に学習する処理、bf16 と組み合わせると壊れやすいです。
- **手間**: 中〜大。T1 と T2 の後に検討します。

#### T4. 勧めないもの
- **フレーム総数による動的バッチ** ([Lhotse DynamicBucketingSampler](https://lhotse.readthedocs.io/en/v1.22/_modules/lhotse/dataset/sampling/dynamic_bucketing.html) など)
  - 重いデコーダーと識別器が固定長なので、長さに比例するのはエンコーダー、事後エンコーダー、flow、MAS だけです。
  - 話者ごとにまとめて取るサンプリングの約束とも衝突します。
  - バケット分けで +34% の前例があります。
- **FlashAttention / SDPA**: テキストエンコーダーは相対位置の注意で、系列も短い (≤400) ため相性が悪いです。T3 (`--attn-drop-rel-v`) で +7% 遅くなっています。
- **fused オプティマイザー、TF32、bf16**: すでに使っています。
- **DataLoader**: 学習は GPU で詰まっています (precomputed mel で +6.5%)。

## 4. まず手元で安く測る価値があるもの

このPC (Ryzen 5900X、RTX 4070 Ti SUPER) だけで、GPU を借りずにできるものです。

1. **flow だけの INT8 の質の評価** (C4、半日)
   - `bench\base_qdq_flow.onnx` と `bench\base_fp32.onnx` で、同じ乱数を使って評価用の文を合成します。
   - `/eval-zs` (cross-utt SECS、2 つの話者エンコーダー)、CER (`piper_train.tools.eval_cer`)、帯域スペクトル、`measure_comb_hnr`、試聴で比べます。
   - 合格すれば −8〜13% が手に入ります。
2. **WASM のスレッドの効果** (C1、1〜2 時間)
   - `src/wasm/openjtalk-web` のデモを、COOP/COEP ヘッダー付きのローカルサーバーで開きます。`numThreads` を 1 / 2 / 4 にして、同じ文の合成時間を比べます。
3. **デコーダーを区切ったときの一致の確認** (C3 の可否、1〜2 時間)
   - 既存の `export_onnx_streaming.py` で zs-v1 を書き出します。余白 10 / 20 / 24 フレームで、区切らない場合と波形がどこまで一致するかを比べます。
   - 計算どおりなら、20 フレーム以上でほぼ一致するはずです。
4. **学習 1 ステップの内訳** (T1〜T3 の前提、半日)
   - 4070 Ti SUPER で、小さいバッチ (例: 8) と既存の小さなデータを使い、`torch.profiler` で G 側 (エンコーダー / flow / デコーダー / MAS / CAM++) と D 側 (MPD / MRD / WavLM) の時間を出します。
   - 「長さで変わる部分」と「固定長の部分」の比率が分かれば、T1 と T3 の上限が決まります。
5. **パディング切り上げ + cuDNN 探索の A/B** (T1、半日)
   - 同じ 300 バッチで次の 3 つを比べます。
     - (a) `--no-cudnn-benchmark`
     - (b) 切り上げ 64 + 探索あり
     - (c) 切り上げ 32 + 探索あり
   - 損失が一致するかのテストも同時に行います。
6. **WavLM の頻度による時間差** (T2、1〜2 時間): `--wavlm-every-n-steps 1 / 2 / 4` で s/step を測ります。質の比較は別途必要です。
7. (参考) **CI の Xeon での FP16 / FP32 の A/B** (`multi-runtime-rtf.yml` の仕組みで): このPCの結論 (差なし) が、x86 サーバーでも同じかを確かめます。
