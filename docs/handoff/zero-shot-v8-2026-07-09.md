### 残 findings 8 施策の実装完了 (2026-07-09 追加、 design doc §3.8)

§3.7 で v8 config を確定した後、 review で未実装だった findings をコード側で完遂。
GPU 実測は次セッション (vast.ai instance destroy 済) だが、 各施策は単体テスト
40+ で契約 pin 済 + backward-compat は byte-for-byte 一致で保証。

**予測 wall-clock 更新** (§3.8 累積効果):

- 現行 sec/step: 10.74 (smoke2 baseline)
- 予測 sec/step: **7-8** (T-empty +2-3% × T-npy +5-10% × T3 +2-5% × T6 +5-10%、
  掛算ではなく overlap 保守見積)
- **単一 A100 SXM4**: 51 日 → **30-38 日** (最良 30 日)
- **4x A100 SXM4 DDP**: 9-11 日 → **6-8 日** (最良 6 日)
- **前処理 (P3/P4/P5)**: 8-10h → **2-4h**

詳細は [design doc §3.8](../design/zero-shot-v8-dataset-scaling-plan.md#38-残-findings-実装完了-2026-07-09-追加ランディング) 参照。

### 実測 (vast.ai A100 SXM4 80GB × 1)

| Test | 設定 | sec/step | Non-finite skip |
|---|---|---|---|
| Test 1 (baseline) | bf16-mixed + SCL + DINO + bucketing、 100 batches | 14.0 | 0/100 |
| **smoke2** ⭐ | + 5 施策 + KL v2、 300 batches | **10.74** | **6/300 (2%)** |
| smoke3b | + `--precomputed-mel` | 11.46 | 6/300 (2%) |

**Improvement**: **-23% sec/step** vs Test 1 (real config で)

### batch size 探索 (追加、 A100 SXM4 80GB × 1)

| batch | VRAM peak | utts/sec |
|---|---|---|
| **64** ⭐ | 40GB | **5.96** (最高) |
| 192 | 63GB | 5.82 |
| 224 | 73GB (91.6%) | 5.15 (-14%) |
| **256** | OOM | — |

→ **compute-bound、 batch 増加で throughput 悪化**。 **v8 本走は batch=32/GPU × 4x DDP (effective 128)** で単一 GPU の最良 utt throughput を維持しつつ並列化。

## v8 本走の推奨構成

**Plan B: 4x A100 SXM4 DDP、 batch=32/GPU (effective 128)**

見積: **9-11 日 / ~$1,120** (storage 込 $5.19/hr × 240 hr)

CLI: [design doc §3.7 参照](../design/zero-shot-v8-dataset-scaling-plan.md#37-全-smoke-test-完了--最終見積-2026-07-09-セッション終了時点)

**除外フラグ (実測で不採用)**:
- `--compile`: torch inductor+triton kernel compile crash
- `--precomputed-mel`: GPU-bound で -6.5% 遅い
- `--enable-length-bucketing`: +34% 逆効果

## 学習開始手順 (次セッション用)

### 1. vast.ai instance 準備 (4x A100 SXM4 想定)

```bash
# search + rent
vastai search offers 'num_gpus=4 gpu_name=A100_SXM4 reliability>0.995 duration>21 disk>1700 inet_up>3'
vastai create instance <ID> --image nvidia/cuda:12.8.1-devel-ubuntu24.04 \
    --disk 1700 --label piper-v8-fullrun \
    --env "-e WANDB_API_KEY=... -e HF_TOKEN=..."
```

### 2. 環境セットアップ (30 分)

```bash
ssh root@<ip>
# torch 2.11 + venv + repo
cd /data && git clone https://github.com/ayutaz/piper-plus.git piper-plus
cd piper-plus && git checkout feat/zero-shot-v8-dataset-scaling
python -m venv /data/piper/.venv
/data/piper/.venv/bin/pip install torch==2.11.0+cu128 torchaudio==2.11.0+cu128 \
    --extra-index-url https://download.pytorch.org/whl/cu128
/data/piper/.venv/bin/pip install -e src/python/[train,super-mas]

# v8 前処理高速化 (#1): hf_transfer (Rust concurrent chunk downloader) を
# 有効化して HF Hub DL を 3-5x 高速化 (200-500MB/s、 単スレッド hf_hub の
# 40-80MB/s 比)。 hf_transfer は src/python[train] extras に同梱済みなので
# あとは env var を export するだけで大丈夫。 Docker image (docker/python-train)
# 側は Dockerfile に `ENV HF_HUB_ENABLE_HF_TRANSFER=1` 済み、 vast.ai bare-VM
# セットアップ時のみ明示 export が必要。
export HF_HUB_ENABLE_HF_TRANSFER=1
echo 'export HF_HUB_ENABLE_HF_TRANSFER=1' >> ~/.bashrc  # 再ログイン時も継続
```

> **有効性の確認**: `python -c "import hf_transfer; import os; print(os.environ['HF_HUB_ENABLE_HF_TRANSFER'])"`
> で `1` が返れば OK。 実 DL の中で `huggingface_hub` が Rust backend を
> 選択したかどうかは `HF_HUB_VERBOSITY=info hf download ...` の log で
> `Using hf_transfer` が出るかで判定できる (未 install なら fallback して
> RuntimeError にはならず単に旧 backend が使われるだけなので、 効いてる
> かどうかは必ず log か speed で確認する)。

### 3. データセット + CAM++ 再構築 (~7-10h、 ~$12-17)

**注意 (2026-07-09)**: vast.ai instance 44096702 は **削除済** (storage 課金停止のため)。
v8 dataset は破棄済みで、 次セッションでフル再構築が必要。

再構築手順 (推定時間、 前処理高速化 impl1-4 反映後 — [design doc §3.11](../design/zero-shot-v8-dataset-scaling-plan.md#311-前処理高速化-4-施策実装完了-2026-07-09-追加ランディング) 参照):

- 生データ DL (moe-speech-plus + LibriTTS-R + AISHELL-3 + CML-TTS + CV pt/ko + Zeroth + KsponSpeech): **1-1.5h** (**impl1 hf_transfer** 有効時、 従来 3-5h から 3-5x 高速化、 §2 環境セットアップ参照)
- `export_libritts_r_from_parquet.py` + `export_cml_tts_from_parquet.py` (impl3 FLAC 直保存): **10-20min** (旧 60-120min から double-decode 消去で 2-6x)
- `prepare_moe_speech_plus.py` (impl4 `--parallel` default ON + chunksize=8): **3-5min** (旧 30-45min から 12-16x)
- **KsponSpeech ETRI PCM→WAV 事前変換は不要** (impl2 で `norm_audio` が `.pcm` を直読、 従来必要だった 3-4h の pre-pass を skip、 §2.4 参照)
- `prepare_multilingual_dataset.py` (P2 並列 VAD + `--ko-*` 引数): **~5-6h** (7-lang 版、 6-lang の場合 ~5h)
- `extract_speaker_embedding.py` (P5 fixed_frames + chunk_batch=128、 default 化済): **~30-45 min** (7-lang ~420k utts、 6-lang ~321k utts)
- `precompute_mel` (--precomputed-mel 使う場合、 実測で効果なしのため任意): 85 sec
- **合計 (6-lang)**: **~6-9h / ~$10-16**
- **合計 (7-lang、 ko 追加)**: **~7-10h / ~$12-17** (単一 A100 storage 込 $1.73/hr、 impl1-4 効果反映)

## 追加ランディング (2026-07-09、 KO 拡張)

**同一 v8 run 内で ko=7 も学習** する副次拡張を feature branch にランディング:

- `LANGUAGE_ID_MAP` / `ALL_LANGUAGES` を 8-lang extended form に拡張
  (ja..pt indices は不変、 sv=6 / ko=7 が新規)
- `parse_zeroth_korean` / `parse_kspon_speech` / `parse_common_voice_ko` を
  `prepare_multilingual_dataset.py` に追加 (既存 aishell3 / cml_tts pattern と同一)
- `export_common_voice_ko.py` を追加 (`export_common_voice_pt.py` ミラー、
  UTMOS tsv 追加サポート)
- 契約 `language-id-map-contract.toml:python_train` を
  `extended_language_id_map` / `extended_languages` に切替
- data-sources.yml に Zeroth-Korean / KsponSpeech / Common Voice ko を追加

**次セッションで必要な追加作業**:

- KsponSpeech は raw `.pcm` (16 kHz mono s16le) を **そのまま** `--ko-ksponspeech`
  に渡す (**impl2 [`2aab2258`](https://github.com/ayutaz/piper-plus/commit/2aab2258)** で
  `norm_audio._read_audio_any` が `.pcm` 拡張子を検出して直読、 従来必要だった
  ~3-4h の ETRI PCM→WAV 変換パスは削除。 既に WAV 化済の場合は
  `audio_ext=".wav"` を渡せば旧経路も維持)
- `python -m piper_train.tools.export_common_voice_ko --cv-dir ...` で CV ko 選別
  (~30 分、 UTMOS tsv を持っていれば同時に投入)
- `prepare_multilingual_dataset.py` に `--ko-zeroth` / `--ko-ksponspeech`
  / `--ko-cv` を追加して再実行 (前処理 wall-clock 想定 +2h)
- 学習 CLI は変更不要 (dataset.jsonl に language_id=7 の utts が入り、
  emb_lang は config.json の `num_languages` から自動的に 7 次元化)
- 評価は §5 の SECS zero-shot に加えて **ko 未知話者の SECS 評価セット** を新設
  (Zeroth の学習除外 spk 5-10 名で計測)
